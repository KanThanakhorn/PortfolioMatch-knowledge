# PortfolioMatch: ร่างแก้รายงานตามสถานะ 1 พฤศจิกายน 2569

> ใช้แทนร่างวันที่ 31 ต.ค. และเทียบกับ `nut-pdf-corrections.md` ก่อนแก้ PDF ฉบับส่ง. ภาพหน้าจอเดิมเป็น mock จาก 31 ต.ค. ไม่ใช่ภาพยืนยัน Gemini.

## 1. ชื่อโครงการ

PortfolioMatch: ต้นแบบระบบช่วยจัดการและคัดกรองใบสมัคร Portfolio (*An Interactive Prototype for Portfolio Admission Screening*).

## 2. ที่มาและความสำคัญ

กรรมการต้องตรวจข้อมูลและเอกสาร Portfolio เทียบหลายเกณฑ์ จึงออกแบบต้นแบบรวมข้อมูลผู้สมัคร สถานะ และเกณฑ์ใน flow เดียว. เมื่อผู้สมัครยินยอม Gemini ช่วยสรุปหลักฐานจาก PDF; กรรมการยังเป็นผู้ตรวจต้นฉบับและตัดสิน. ยังไม่มีผลวัดว่าลดเวลา เพิ่มความแม่นยำ หรือเพิ่มความเป็นธรรม.

## 3. วัตถุประสงค์

1. สาธิต flow ตั้งแต่ตั้งรอบรับสมัครจนถึง Approve/Reject.
2. ตรวจข้อมูลแบบฟอร์มและแสดงข้อมูลผู้สมัครกับสถานะในเบราว์เซอร์เดียว.
3. สาธิต AI ช่วยสรุปหลักฐานตามเกณฑ์เมื่อได้รับความยินยอม โดยไม่ตัดสินแทนกรรมการ.
4. อธิบายข้อจำกัดและความเสี่ยงของการใช้ AI ในการรับสมัคร.

## 4. กลุ่มเป้าหมาย

อาจารย์/กรรมการรับสมัครใช้รายชื่อ รายละเอียด และผล AI เป็นข้อมูลประกอบ; ผู้สมัครอ่านเกณฑ์ กรอกข้อมูล เลือก PDF และเลือกว่าให้ AI วิเคราะห์หรือไม่. เดโมยังใช้ข้อมูลในเบราว์เซอร์เดียวกัน.

## 5. ขอบเขต

**มีแล้ว:** รอบรับสมัครตัวอย่าง, ฟอร์มและ validation, ข้อมูลผู้สมัครใน localStorage, ค้นหาชื่อ/โรงเรียน, รายละเอียด, Approve/Reject, Dashboard และ Gemini วิเคราะห์ PDF แบบ opt-in ผ่าน Next.js Route Handler. ผู้สมัครตัวอย่างเดิมยังใช้คะแนน mock.

**ยังไม่มี:** database, authentication, การเก็บ PDF ต้นฉบับ, การซิงก์ข้ามเครื่อง, rate limit, audit log และหลายรอบที่แยกข้อมูลจริง. Filter/Sort เป็นงานเพิ่ม.

## 6. การทบทวนวรรณกรรม

NIST AI RMF 1.0 ใช้ตั้งกรอบความเสี่ยงและการประเมิน AI; UNESCO Guidance for Generative AI in Education and Research ใช้อภิปรายบทบาทมนุษย์; WCAG 2.2 ใช้เป็นแนวทางฟอร์มและข้อความผิดพลาด. ดู URL ใน `sources.md`. แหล่งเหล่านี้เป็นหลักการออกแบบ ไม่ใช่หลักฐานว่า PortfolioMatch มีประสิทธิภาพสูงขึ้น. ควรเพิ่มงานวิจัยเฉพาะด้านการคัดกรอง Portfolio/AI admissions หากอาจารย์ต้องการ literature เชิงเปรียบเทียบ.

## 7. วิธีดำเนินงานและสถาปัตยกรรม

ออกแบบ User Flow → สร้าง UI ด้วย Next.js App Router, React, TypeScript, CSS และ Lucide → เก็บรอบ/ผู้สมัคร/ผล AI ใน localStorage → ทดสอบ System Flow. เมื่อผู้สมัครติ๊กยินยอม หน้าเว็บส่ง PDF และ requirement ไป `/api/analyze-portfolio`; Route Handler ตรวจไฟล์แล้วส่ง Gemini API พร้อม JSON schema; ผลกลับมาเก็บใน localStorage. ไม่มี database หรือ file storage. API key อยู่ฝั่งเซิร์ฟเวอร์. ดู `assets/system-architecture.svg` และ `assets/user-flow.svg`.

## 8. ผลการดำเนินงานและทรัพยากร

มี Dashboard, Applicants, Detail, Create, Application Form, Submission Success และ Privacy. ผู้สมัครตัวอย่าง 4 รายมีคะแนน mock 92, 86, 74, 61 (เฉลี่ยปัดเป็น 78). ใบสมัครใหม่ที่ยินยอมและวิเคราะห์สำเร็จจึงมีคะแนน Gemini; หากไม่ยินยอมหรือ API ผิดพลาด ใบสมัครยังบันทึกได้แต่ไม่มีคะแนน AI. ภาพ PNG ใน `assets/` ถ่ายจากข้อมูล mock ก่อนเชื่อม Gemini.

ทีม 3 คน: กานต์ flow/integration, ตง Frontend QA/demo, นัท report/presentation. เครื่องมือ: คอมพิวเตอร์ของทีม, Next.js/React/TypeScript/CSS/Lucide, Gemini API. **ให้ทีมเติมจำนวนชั่วโมง อุปกรณ์ที่ใช้จริง ค่า API ตาม usage จริง และตารางต้นทุน–ประโยชน์ก่อนส่ง**; ยังไม่มีตัวเลขยืนยัน และไม่ควรอ้าง ROI ที่ไม่ได้คำนวณ.

## 9. การประเมินและทดสอบ

`npm run typecheck` และ `npm run build` ผ่าน. กานต์ทดสอบ System Flow การสร้างรอบ/ส่ง PDF/รีเฟรช/Approve-Reject/ตัวเลข Dashboard, ไฟล์ผิดชนิด/เกิน 50 MB และป้ายสถานะมือถือ 390×844. Endpoint Gemini ทดสอบกับ PDF จำลองหนึ่งหน้าแล้วได้ HTTP 200 พร้อมคะแนนและหลักฐาน. **ยังไม่ได้ยืนยันผล AI ผ่าน UI จริงหรือ responsive ทุกส่วนพร้อมภาพหลักฐานบนเบราว์เซอร์เป้าหมาย**; ให้ตง retest และใส่ Pass/Fail, browser/version, วันที่, viewport, screenshot, issue. รายงาน QA 30–31 ต.ค. เป็น baseline ก่อนแก้ล่าสุด.

ความเสี่ยง: โมเดลอาจสรุปผิด, ข้อมูลส่วนบุคคลถูกส่งไปภายนอกเมื่อยินยอม, API หนาแน่น/โควตาหมด, คะแนนอาจชักนำกรรมการ, ข้อมูล localStorage สูญหาย. แนวทาง: ยินยอมแยก, ใช้ข้อมูลจำลอง, แสดงข้อจำกัด, กรรมการตรวจต้นฉบับ, เพิ่ม authentication/rate limit/storage และทดสอบคุณภาพ AI ก่อนใช้งานจริง.

## 10. สรุปและพัฒนาต่อ

ต้นแบบแสดง flow รับสมัครและการตัดสินในเบราว์เซอร์เดียว พร้อม Gemini ช่วยสรุป PDF แบบ opt-in ที่ endpoint. ยังไม่ใช่ระบบรับสมัครหลายเครื่องและไม่เก็บ PDF ต้นฉบับ. ขั้นต่อไปคือ database, file storage, authentication, rate limit, audit log, การประเมินคุณภาพ/ความเป็นธรรมของ AI และ usability/performance test กับผู้ใช้จริง.

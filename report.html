01 / Project Title

ชื่อโครงการ

PortfolioMatch: ต้นแบบระบบช่วยจัดการและคัดกรองใบสมัคร Portfolio เป็นชื่อที่สื่อถึงการเปรียบเทียบข้อมูลผู้สมัครกับเกณฑ์ของสาขา สำหรับรายงานภาษาอังกฤษใช้ PortfolioMatch: An Interactive Prototype for Portfolio Admission Screening.

นัท: ตรวจชื่อโครงการและชื่อสมาชิกตามหน้าปกรายงานจริงก่อนส่ง

02 / Background and Motivation

ที่มาและความสำคัญ

การรับสมัครรอบ Portfolio มีข้อมูลส่วนตัว ผลงาน และเกณฑ์พิจารณาหลายส่วน กรรมการต้องเปิดเอกสารและเปรียบเทียบผู้สมัครด้วยตนเอง ทีมจึงออกแบบหน้าจอรวมข้อมูลและแสดงสถานะการพิจารณาในที่เดียว เพื่อลดขั้นตอนสลับเอกสารและช่วยให้การพิจารณาอ้างอิงเกณฑ์เดียวกัน

ต้นแบบมี Gemini วิเคราะห์ PDF ตามเกณฑ์เมื่อผู้สมัครยินยอม โดยกรรมการยังตัดสินใจเอง; endpoint ผ่านการทดสอบด้วย PDF จำลองแล้ว แต่ UI ผล AI ยังต้องทดสอบซ้ำ และยังไม่มีผลวัดว่าใช้เวลาน้อยลงหรือแม่นยำขึ้น

03 / Project Objectives

วัตถุประสงค์

  1. สร้างต้นแบบ flow ตั้งแต่กำหนดรอบรับสมัครจนถึงการตัดสินใจของกรรมการ
  2. รวมข้อมูลผู้สมัคร สถานะ และคะแนนตัวอย่างให้เห็นจากหน้าจอเดียวกัน
  3. ตรวจรูปแบบข้อมูลสำคัญก่อนบันทึกใบสมัครสาธิต
  4. สื่อสารข้อจำกัดและความเสี่ยงของการใช้ AI ในงานรับสมัครอย่างตรงไปตรงมา

เกณฑ์ประเมินต้นแบบ: เปิดหน้าได้, ส่งข้อมูลสาธิตได้, รายชื่อและ dashboard อัปเดต, Approve/Reject คงอยู่ในเบราว์เซอร์เดิม

04 / Target Users

กลุ่มเป้าหมาย

อาจารย์ / กรรมการรับสมัคร

ต้องการเห็นรายชื่อ ข้อมูล และสถานะในมุมมองเดียว ใช้ข้อมูลประกอบการตัดสินใจและตรวจหลักฐานต้นฉบับก่อนอนุมัติ

นักเรียน / นักศึกษาผู้สมัคร

ต้องการทราบเกณฑ์ของรอบสมัคร กรอกข้อมูล เลือก PDF และรับคำยืนยันว่าข้อมูลเดโมถูกบันทึกในเบราว์เซอร์

05 / System Scope

ขอบเขตของระบบ

Core ของต้นแบบ

ตั้งค่ารอบตัวอย่าง, ฟอร์มตรวจข้อมูล, บันทึกผู้สมัครใน localStorage, ค้นหาชื่อ/โรงเรียน, ดูรายละเอียด, Approve/Reject, dashboard และ Gemini วิเคราะห์ PDF แบบยินยอม

Optional / Future Work

ฐานข้อมูลและบัญชีผู้ใช้, จัดเก็บ PDF ต้นฉบับ, การรับสมัครหลายรอบ, Filter/Sort, Audit log, rate limit และการทดสอบ AI กับผู้ใช้จริง

06 / Literature Review

แนวคิดและเอกสารอ้างอิง

แหล่งอ้างอิงต่อไปนี้ใช้เป็นพื้นฐานด้านความเสี่ยง AI, บทบาทมนุษย์ และการออกแบบฟอร์ม ไม่ใช่หลักฐานว่า PortfolioMatch มีประสิทธิภาพสูงขึ้นแล้ว

  1. NIST (2023), AI Risk Management Framework 1.0. ใช้ระบุความจำเป็นในการประเมินความเสี่ยง ความน่าเชื่อถือ และอคติของระบบ AI ก่อนใช้งานจริง เอกสารต้นฉบับ ↗
  2. UNESCO (2023), Guidance for Generative AI in Education and Research. ใช้สนับสนุนแนวคิดการคงบทบาทมนุษย์และการใช้ AI อย่างระมัดระวังในบริบทการศึกษา เอกสารต้นฉบับ ↗
  3. W3C (2024), WCAG 2.2. ใช้อ้างอิงเรื่องป้ายชื่อช่องกรอกและการระบุข้อผิดพลาดในฟอร์ม เช่น Success Criteria 3.3.1 และ 3.3.2 มาตรฐานต้นฉบับ ↗

นัท: จัดรูปแบบบรรณานุกรมตามรูปแบบที่อาจารย์กำหนด และเพิ่มงานวิจัยเฉพาะด้านการคัดกรอง Portfolio หากหาแหล่งที่ตรวจสอบได้

07 / Methodology and Architecture

วิธีดำเนินงานและสถาปัตยกรรม

เริ่มจากกำหนดผู้ใช้และ flow จากนั้นออกแบบหน้าจอและข้อมูลตัวอย่าง พัฒนาด้วย Next.js App Router, React, TypeScript และ CSS. ฝั่ง Client จัดการ form และ interaction; localStorage เก็บรอบรับสมัคร ผู้สมัคร และผล AI ในเบราว์เซอร์เดียว; sessionStorage จำหน้าสำเร็จในแท็บเดิม. เมื่อผู้สมัครยินยอม Next.js Route Handler ส่ง PDF ชั่วคราวและเกณฑ์ไป Gemini API

มี Route Handler สำหรับ Gemini API เท่านั้น; ยังไม่มี backend สำหรับใบสมัคร, database, authentication, file storage หรือข้อมูลข้ามเครื่อง

08 / Project Results

ผลการดำเนินงาน

ต้นแบบมีหน้า Dashboard, Applicants, Applicant Detail, Create Admission และ Application Form พร้อมหน้าสำเร็จหลังส่งใบสมัคร. ข้อมูลเริ่มต้นมีผู้สมัครตัวอย่าง 4 คน; คะแนนเฉลี่ยที่แสดงจาก 92, 86, 74 และ 61 คือ 78% เมื่อปัดเป็นจำนวนเต็ม. ตัวเลขนี้เป็นข้อมูล mock สำหรับผู้สมัครตัวอย่าง ไม่ใช่ผล Gemini; ใบสมัครใหม่ที่ยินยอมและวิเคราะห์สำเร็จจึงมีคะแนน AI

สมาชิก 3 คนตามแผนงาน: กานต์ดู flow และ integration, ตงดู QA และเสถียรภาพเดโม, นัทดูรายงาน สไลด์ และ UX/research. เครื่องมือใน repo ได้แก่ Next.js, React, TypeScript, CSS และ Lucide. ยังไม่มีข้อมูลชั่วโมงทำงาน ค่าอุปกรณ์ หรือค่าใช้บริการ Gemini ที่ยืนยันแล้ว นัทควรเติมจากข้อมูลจริงของทีมก่อนวิเคราะห์ต้นทุน–ประโยชน์

09 / Evaluation and Testing

การประเมินผลและการทดสอบ

รายงาน QA ของตงลงวันที่ 30–31 ต.ค. 2569 เป็น baseline ก่อนแก้ล่าสุด. กานต์ตรวจ TypeScript/build, System Flow, ไฟล์ผิดชนิด/เกิน 50 MB, Reject หลังรีเฟรช และป้ายสถานะมือถือแล้ว. Endpoint Gemini ผ่านกับ PDF จำลอง (HTTP 200); UI ที่ใช้ Gemini จริงและ responsive ทุกส่วนยังรอ retest พร้อมภาพหลักฐานจากตง

กรณีสถานะล่าสุดหลักฐาน/ข้อจำกัด
Typecheck / Buildผ่านคำสั่ง npm run typecheck และ npm run build
ส่งฟอร์มโดยไม่มี PDFผ่านแสดงข้อผิดพลาดและไม่สร้างรายการ
ส่งพร้อมไฟล์ .pdf และรีเฟรชผ่านในเดโมบันทึกข้อมูลและชื่อไฟล์ ไม่เก็บเนื้อไฟล์
Approve → Dashboardผ่านสถานะและยอดรวมเปลี่ยนในเบราว์เซอร์เดียวกัน
Reject / PDF ผิดชนิด / ไฟล์เกิน 50 MBผ่าน System Flowกานต์ทดสอบแล้ว; ตงควร retest บนเบราว์เซอร์เป้าหมาย
Gemini APIผ่านที่ endpointPDF จำลอง → HTTP 200; ยังไม่ยืนยันการแสดงผลผ่าน UI จริง
มือถือทุกส่วนและภาพหลักฐานรอ retestป้ายสถานะถูกแก้แล้ว แต่ยังต้องเก็บภาพครบหน้า

อย่าแปลงรายการ “รอทดสอบซ้ำ” เป็น “ผ่าน” จนกว่าจะมีหลักฐาน

10 / Conclusion and Future Work

สรุป ข้อจำกัด และแนวทางพัฒนาต่อ

PortfolioMatch แสดง flow ของการรับสมัคร Portfolio และการพิจารณาผู้สมัครในรูปแบบ interactive prototype ได้ โดยข้อมูลหน้า Dashboard รายชื่อ และรายละเอียดใช้ข้อมูลชุดเดียวกันภายในเบราว์เซอร์ ขณะนี้ยังสรุปไม่ได้ว่าระบบลดเวลาในการตรวจหรือเพิ่มความถูกต้อง เพราะยังไม่มีการวัดกับผู้ใช้จริง

ข้อจำกัดหลักคือข้อมูลไม่ซิงก์ข้ามเครื่อง, ไม่เก็บเนื้อไฟล์ PDF, ไม่มีสิทธิ์ผู้ใช้หรือ rate limit และยังมี QA ของ UI Gemini/มือถือที่ต้องทดสอบซ้ำ. ขั้นต่อไปคือเพิ่ม backend/database/file storage, สิทธิ์และ audit log, ประเมินคุณภาพและความเป็นธรรมของ AI และทดสอบกับผู้ใช้จริง
